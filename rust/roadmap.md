

这份路线把 course.md 的章节变成可执行的学习安排。默认每周 5 天、每天 45 到 90 分钟；时间更少时只保留“动手”和“完成检查”，不要只读不写。每个阶段结束都要留下代码、测试或复盘文件，不能用“看过文章”作为完成标准。

## 使用规则

每次学习固定分四段：

1. 10 分钟：阅读当天章节，写下三个预测。
2. 30 到 60 分钟：在自己的 Cargo 项目中手写示例和练习。
3. 10 分钟：运行检查命令，保留错误输出或测试结果。
4. 5 分钟：写一段复盘，说明数据所有权、错误路径和下一步。

建议建立如下本地目录：

```text
rust-lab/
├── Cargo.toml
├── src/
│   └── main.rs
├── examples/
├── tests/
└── notes/
    ├── mistakes.md
    └── weekly.md
```

每天开始前运行：

```bash
cargo check
cargo test
cargo fmt --check
```

如果项目暂时没有测试，仍运行 cargo test，让“没有测试”成为需要补齐的提醒，而不是被忽略的状态。

| --- | --- | --- | --- |
| 1. 工具链和表达式 | 第 1 周 | 第 0 至 1 章 | 可运行的学习记录程序 |

## 每周节奏

- 周一：学习新概念，完成最小示例。
- 周二：不看示例重写，故意制造一个编译错误。
- 周三：完成章节练习，把输入和输出写成测试。
- 周四：改造结构，减少重复和不必要的 clone。
- 周五：运行完整检查，整理 mistakes.md，决定下周唯一重点。
- 周末可选：阅读 resources.md 中与当前阶段对应的一个 GitHub 项目，不把阅读替代练习。

# 阶段 1：工具链和表达式

## 阶段目标

建立 Cargo 工作流，能够读懂变量、函数、条件和循环的类型错误。这个阶段不追求复杂功能，重点是让编译、运行、测试成为肌肉记忆。

## 第 1 天：创建项目

执行：

```bash
cargo new rust-lab
cd rust-lab
cargo run
cargo check
cargo test
```

练习：

- 把 main 改成输出今天的主题、日期文字和学习分钟数。
- 删除一个分号，观察表达式返回值变化。
- 在 notes/weekly.md 记录三条命令的差异。

产出：一个能运行的 Cargo 项目和第一条学习记录。

## 第 2 天：变量和类型

练习：

- 写 u32、i32、f64、bool 和 String 的变量。
- 为两个不同数值类型写转换函数，不依赖隐式转换。
- 使用 mut 修改学习计数，但保持主题字符串不可变。

检查：

```bash
cargo fmt
cargo check
```

验收：能指出每个变量的类型，并解释为什么 Rust 不自动混合整数类型。

## 第 3 天：条件和 match

练习：

- 写分数等级函数。
- 写命令字符到动作名称的 match。
- 让 match 少一个分支，记录编译器如何提醒你。

产出：src/main.rs 中至少两个返回值函数。

## 第 4 天：循环和函数

练习：

- 用 for 计算 1 到 100 的偶数和。
- 用 while 模拟重试次数。
- 用 loop 找到第一个满足条件的数字。
- 把一个长 main 拆成三个有类型签名的函数。

## 第 5 天：阶段检查

不要看前三天的代码，重新写一个“学习计时器”：

- 接收一个模拟的学习分钟数；
- 根据分钟数返回状态；
- 统计一周的总分钟数；
- 至少写一个测试；
- 让 cargo fmt、cargo check、cargo test 全部通过。

阶段完成标准：

- [ ] 能独立创建 Cargo 项目。
- [ ] 能解释语句和表达式的差异。
- [ ] 能读懂 mismatched types 和 non-exhaustive patterns。
- [ ] 有一个可运行、可测试的小程序。

卡点处理：如果被类型错误卡住超过 20 分钟，保留错误文本，缩小到最小复现函数，再继续；不要直接复制完整答案。

# 阶段 2：数据建模和集合

## 阶段目标

学会选择 String、Vec、HashMap、struct、enum 和 Option。阶段结束时要有一个只存在内存中的任务列表。

## 第 6 天：String 和 str

练习：

- 写一个只读函数，参数使用 str 的借用。
- 写一个返回新 String 的格式化函数。
- 处理中文标题，使用 chars 或 lines，而不是整数索引。
- 对空白标题调用 trim，并决定是否拒绝。

验收：能解释何时返回 String，何时返回引用。

## 第 7 天：Vec

练习：

- 实现添加任务、列出任务和删除最后一项。
- 使用 enumerate 打印序号。
- 用 iter、iter_mut 和 into_iter 各做一次操作，写出三者所有权差异。
- 测试空 Vec 和只有一项的 Vec。

## 第 8 天：HashMap

练习：

- 统计任务标签出现次数。
- 使用 entry API 实现不存在就插入、存在就加一。
- 处理查询不到的键，返回 Option。
- 比较 Vec 顺序查找和 HashMap 键查找的使用场景。

## 第 9 天：struct 和 impl

建立 Task：

```rust
struct Task {
    id: u32,
    title: String,
    done: bool,
}
```

练习：

- 添加 new、finish、is_done 方法。
- 让 new 拒绝空标题，先用 Option 或 Result 表达。
- 为任务增加优先级字段，并说明字段类型选择。

## 第 10 天：enum 和 Option

练习：

- 定义 Add、List、Done、Remove、Quit 命令。
- 用 match 将命令转成业务动作。
- 用 Option 表达按 id 找不到任务。
- 删除用特殊数字表示失败的旧逻辑。

阶段完成标准：

- [ ] 有一个 Task struct 和至少三个方法。
- [ ] 有一个命令 enum，match 覆盖全部变体。
- [ ] 查询不到任务时不会 panic。
- [ ] 至少有五个测试，包含空输入和不存在 id。

卡点处理：如果代码中出现大量 String 比较，停下来检查是否应该使用 enum；如果每个函数都 clone，检查哪个对象应该拥有状态。

# 阶段 3：所有权、借用和错误

## 阶段目标

把编译器当作设计反馈。阶段结束时，任务库应该有清楚的所有权边界、自定义错误和测试。

## 第 11 天：移动和返回所有权

练习：

- 把 Task 传给按值函数，观察移动。
- 改成借用读取版本。
- 写一个修改后返回 String 的函数。
- 分别演示 Copy 类型和 String 类型的赋值行为。

复盘问题：

- 这个函数需要拥有数据，还是只需要查看数据？
- 如果函数失败，谁负责保留原来的值？
- clone 是业务需要，还是为了绕过错误？

## 第 12 天：共享借用

练习：

- 用 &[Task] 实现查询。
- 用 &mut [Task] 实现批量完成。
- 写一个返回任务标题切片的函数。
- 构造并修复一次冲突借用。

检查：

```bash
cargo check
cargo test
```

验收：能用一句话说明每个引用的来源和最大存活范围。

## 第 13 天：生命周期

不要一开始给所有函数加生命周期。先写：

- 返回新 String 的版本；
- 返回输入引用的版本；
- 接受两个字符串并返回较长者的版本。

然后比较三种签名，说明哪些数据被拥有，哪些数据被借用。

## 第 14 天：Result 和自定义错误

定义：

```rust
enum TaskError {
    EmptyTitle,
    MissingTask(u32),
    InvalidCommand,
}
```

练习：

- 添加任务时拒绝空标题。
- 完成和删除时返回 MissingTask。
- 把解析错误和业务错误分开。
- 在 main 边界将错误打印成中文信息。

## 第 15 天：模块

拆成：

```text
src/
├── main.rs
├── task.rs
└── error.rs
```

要求：

- task.rs 保存 Task 和业务方法；
- error.rs 保存错误类型；
- main.rs 只做流程编排；
- 不让 main 直接修改 Task 的私有字段。

## 第 16 天：测试和阶段复盘

至少写：

- 新增正常任务；
- 拒绝空标题；
- 完成已有任务；
- 完成不存在任务；
- 删除任务后数量减少；
- 查询空列表。

运行：

```bash
cargo fmt
cargo clippy -- -D warnings
cargo test
```

阶段完成标准：

- [ ] 核心业务函数不需要 clone 才能通过。
- [ ] 所有用户输入失败都返回 Result。
- [ ] 业务错误能区分至少三种原因。
- [ ] 模块和测试可以独立阅读。
- [ ] 能解释一次借用错误的根因，而不是只说“加了 clone”。

卡点处理：先保留原始错误，再把函数缩成十行以内的最小示例；只有确认所有权边界后才改回项目。

# 阶段 4：抽象和并发

## 阶段目标

用 trait、泛型和迭代器减少重复，再用线程和消息通道构造可控的 worker。不要为了展示 API 而并发，先明确共享状态和退出协议。

## 第 17 天：trait 和泛型

练习：

- 为 Task 实现 Summary trait。
- 写一个泛型函数寻找最大值。
- 给函数加最小的 trait bound，不要一次写过多约束。
- 把重复的打印逻辑替换成 trait 方法。

## 第 18 天：迭代器和闭包

练习：

- 用 filter 找未完成任务。
- 用 map 生成标题列表。
- 用 collect 收集新 Vec。
- 比较迭代器和手写 for 的可读性。
- 给闭包加 move，观察捕获变量的变化。

验收：能指出迭代器链的消费点。

## 第 19 天：线程

练习：

- 启动两个线程计算不同区间。
- 用 join 收集结果。
- 让线程返回 Result，而不是在内部 panic。
- 记录哪些数据必须 move 进线程。

## 第 20 天：共享状态

练习：

- 用 Arc 共享只读配置。
- 用 Arc 和 Mutex 保护计数器。
- 缩短锁的作用域。
- 不在持锁期间执行睡眠、文件或网络操作。

## 第 21 天：channel 和退出

设计消息：

```rust
enum WorkerMessage {
    Add(String),
    Stop,
}
```

要求：

- 主线程拥有任务状态；
- worker 只接收消息；
- Stop 后 worker 必须退出；
- 发送端关闭后，接收端能结束循环；
- 测试至少覆盖一条 Add 和一次 Stop。

## 第 22 天：阶段复盘

用一页文档比较：

| 方式 | 状态所有者 | 适合场景 | 主要风险 |
| --- | --- | --- | --- |
| 直接共享可变数据 | 多个线程 | 少量同步状态 | 锁竞争 |
| Arc 与 Mutex | 一个共享状态 | 简单计数和缓存 | 死锁、锁范围 |
| channel | 单一状态拥有者 | 命令和事件 | 关闭协议 |

阶段完成标准：

- [ ] 能为共享状态选择 Mutex 或 channel 并解释原因。
- [ ] worker 有明确的停止路径。
- [ ] 没有用 unsafe 逃避 Send 或 Sync 错误。
- [ ] 能指出并发测试中可能存在的时序问题。

# 阶段 5：异步和工程

## 阶段目标

理解 Future、runtime、spawn 和 async channel，把同步任务模型扩展成异步事件处理。异步是工程选择，不是课程终点。

## 第 23 天：Tokio 项目

创建独立项目：

```bash
cargo new async-lab
cd async-lab
cargo add tokio --features macros,rt-multi-thread,time,sync
cargo run
```

如果 cargo add 不可用，手动编辑 Cargo.toml，并运行 cargo check。

## 第 24 天：Future 和 await

练习：

- 写一个 async 函数，等待定时器后返回 String。
- 使用 #[tokio::main] 启动 runtime。
- 不调用 await，观察 Future 不会执行。
- 用 Result 处理异步任务的失败。

## 第 25 天：并发任务

练习：

- 启动两个不同延迟的任务。
- 使用 JoinHandle 等待结果。
- 记录任务 panic 与业务 Err 的区别。
- 为任务增加超时或取消思路，但先不追求完整实现。

## 第 26 天：异步 channel

练习：

- 用 mpsc 发送任务命令。
- 由一个消费者拥有状态。
- 发送 Stop 后正常退出。
- 测试接收到的消息顺序。

## 第 27 天：工程检查

运行：

```bash
cargo fmt --check
cargo check
cargo clippy -- -D warnings
cargo test
```

检查清单：

- async 函数没有执行长时间同步阻塞；
- 任务错误没有被静默丢弃；
- channel 的发送端在退出前能关闭；
- 共享状态的所有权边界写在模块接口上。

## 第 28 天：阶段复盘

写一页比较同步和异步：

- 是否有大量等待外部资源？
- 是否需要并发处理多个连接或事件？
- runtime 的生命周期由谁拥有？
- 失败、取消和优雅退出怎么传播？

阶段完成标准：

- [ ] 能解释 Future 只描述工作，runtime 才负责执行。
- [ ] 能启动多个任务并等待结果。
- [ ] 能用异步 channel 传递命令。
- [ ] 能指出一个不适合 async 的 CPU 密集任务。

# 阶段 6：综合项目

## 阶段目标

完成 project-tutorial.md 中的任务管理器。先完成标准库同步版，再根据需求增加持久化和异步扩展。

## 第 29 天：项目设计

先写设计，不写实现：

- 用户能执行哪些命令？
- Task 的最小字段是什么？
- 哪些操作可能失败？
- 内存仓库是否应该拥有 Task？
- 文件格式和异步扩展是否属于第一版？

提交一张模块图和一张错误路径表。

## 第 30 天：领域模型

实现：

- Task；
- TaskError；
- Command；
- 内存仓库；
- 新增、列出、完成、删除。

验收：每个业务函数都有清楚的输入、输出和失败类型。

## 第 31 天：测试优先

先写测试再补实现：

- 空标题失败；
- id 连续生成；
- 完成状态变化；
- 删除后查询不到；
- 不存在 id 返回错误；
- 列出顺序稳定。

每完成一个测试就运行 cargo test，不要积累十个失败。

## 第 32 天：命令行边界

把终端输入解析为 Command，业务层不读取 stdin。测试通过直接构造 Command 完成，不依赖真实终端。

## 第 33 天：文件持久化

为持久化定义独立边界：

- 读取文件失败返回 I/O 错误；
- 空文件有明确行为；
- 写入失败不伪装成成功；
- 使用临时路径测试，不覆盖正式数据；
- 保存失败时内存状态是否仍然保留，要写清楚决定。

## 第 34 天：异步扩展

只有在同步版稳定后再做：

- 把事件发送改为 Tokio mpsc；
- 让一个任务拥有仓库；
- 增加优雅退出；
- 不把所有函数机械改成 async；
- 对比同步和异步版本的测试成本。

## 第 35 天：最终验收

运行：

```bash
cargo fmt --check
cargo check
cargo clippy -- -D warnings
cargo test
```

写最终复盘：

- 我最容易犯的 Rust 错误是什么？
- 哪个类型设计消除了非法状态？
- 哪一处借用边界最重要？
- 为什么最终选择同步或异步？
- 下一步要补哪个资源，而不是泛泛地“继续学习”？

最终项目通过标准：

- [ ] 文档中的所有核心命令都能运行。
- [ ] 至少有新增、查询、完成、删除和错误输入测试。
- [ ] 业务层不直接读终端或打印错误。
- [ ] 错误类型能帮助调用者做决定。
- [ ] 没有为了通过编译而无理由 clone。
- [ ] 退出路径和资源清理是可解释的。
- [ ] project-tutorial.md 中的阶段任务全部有结果记录。

# 卡点处理手册

## 编译错误

1. 先读第一条真正的 error，不要从最后一屏开始猜。
2. 找到文件、行号和编译器标出的类型。
3. 回到函数签名，判断问题是所有权、借用、类型还是作用域。
4. 写出十行以内的最小复现。
5. 修复后把原因记录到 notes/mistakes.md。

## 运行时行为不对

- 先给函数增加测试，不要先加日志到处打印。
- 固定输入和期望输出。
- 检查迭代器是否真的消费。
- 检查线程是否 join，channel 是否关闭。
- 异步代码检查 Future 是否 await、runtime 是否存活。

## 不知道是否该引入依赖

先回答：

- 标准库能否清楚完成？
- 依赖是否解决当前阶段的真实问题？
- 依赖增加了什么编译和版本成本？
- 是否能在 Cargo.toml 中记录用途？

如果只是为了省几行代码，先用标准库完成学习目标。

## 学习进度落后

不要跳过所有权和 Result。可以缩短项目范围：

- 先只做内存版本；
- 先只支持三个命令；
- 先只写纯函数；
- 异步和持久化放到最后；
- 每周只保留一个可验收产出。

# 阶段切换检查

进入下一阶段前，必须同时满足三件事：

1. 代码能运行；
2. 测试能证明一个成功路径和一个失败路径；
3. 能用自己的话解释本阶段最重要的所有权或错误边界。

只满足“看懂了”不切换阶段。课程正文见 course.md，完整项目步骤见 project-tutorial.md，GitHub 项目的使用时机见 resources.md。
