# Python RPG 精简交付路线图

**目标：** 交付一个可离线游玩的个人 Python 战术 RPG。玩家能编写 Python、执行回合、完成六关战役，并在刷新后继续游戏。

**当前状态：** 阶段 1 的战斗内核与 Replay 已完成；阶段 2 的本地 CPython Runner 已完成。后续工作只围绕可玩应用和战役内容展开。

> **最高优先级：** 这是个人使用、仅在本机运行的游戏。任何功能、防护、抽象或测试，若不能直接改善本地单人游玩，或没有对应的真实问题，默认不做。

**架构：** 战斗内核是唯一规则来源；Runner 只读取 `WorldView` 并返回候选 `TurnCommand`；应用层负责交互和存档；战役层提供关卡、奖励与解锁。下游不得复制上游公共类型。

**技术栈：** 以 `rpg/package.json` 和 lockfile 为准。核心使用 Vite、TypeScript、Vitest、本机 CPython 3.12+、Node WebSocket、CodeMirror；Playwright 只承担关键流程验收。

## 产品与工程边界

- 本项目是单人本机游戏，不是公网服务，不做账号、权限、多用户和云同步，也不接收网络输入的玩家代码。
- Runner 是本地代码执行器，采用“信任本地代码”模型。保留 loopback 监听和模块白名单，作用是避免误操作，不把它扩展成对抗恶意代码的隔离边界。
- 优先交付玩家能直接感知的内容：编辑代码、执行回合、战斗反馈、关卡推进和存档。
- 新功能必须服务当前六关主流程；只为未来设想、接口对称或“也许有用”而增加的能力直接延期。
- 防护措施必须对应本地正常使用中已经复现的故障；不按公网产品、恶意用户或多租户系统的标准设计。
- 只处理正常使用中常见的失败：语法错误、运行时错误、超时、Runner 不可用、存档 JSON 损坏。
- 不为极端进程竞态、重复关闭、信号组合、跨平台边角行为或理论上的未来扩展增加状态机和抽象层。
- 现有稳定测试不为减少数量而删除；重复、脆弱或只验证实现细节的测试可在相关代码改动时合并或移除。

## 验证原则

- 每个改动只运行直接相关的测试；阶段完成时再运行一次完整单元测试和生产构建。
- 核心规则覆盖“正常路径 + 一个关键失败路径”，不为同一行为排列所有输入、平台和时序组合。
- Playwright 只保留一条完整通关主流程，以及确有用户价值的少量失败流程。
- 不要求每个小任务都执行完整测试、独立复审和单独提交。按可独立说明、可独立回滚的逻辑提交即可。
- 测试失败先判断是否暴露真实玩家问题；若只是过度严格的旧断言，优先简化测试和契约。

## 阶段 4：六关战役与内容

- [ ] 先完成前三关的可玩垂直切片，再沿用同一结构扩展到六关。
- [ ] 保持关卡 ID `python-marsh-01` 至 `python-marsh-06`，每关包含初始世界、目标、隐藏断言、参考解法和奖励。
- [ ] 使用简单 TypeScript 数据或 JSON 加载器；只检查必填字段、重复 ID 和实际引用，不建设通用 schema/decoder 框架。
- [ ] 候选命令先通过关卡断言，再交给 `resolveTurn`；胜利后解锁下一关并保存进度。
- [ ] 重试直接从关卡初始状态重新创建战斗，不实现复杂恢复或补偿事务。
- [ ] 素材只登记实际使用项及来源，不建设独立素材账本系统。

**阶段验收：** 每关用一份参考解法验证可通关；最后用一条 Playwright 流程从第一关打到第六关，检查解锁、奖励和刷新恢复。

## 止损规则

- Runner 常驻进程在正常玩法中仍频繁失效：改为每次运行启动一个 Python 子进程，保留现有 `RunnerPort` 接口。
- 应用外壳被存档或恢复逻辑拖慢：先只保存关卡、代码和战斗状态，延期导入导出与历史兼容。
- 前三关尚未形成完整乐趣循环：暂停后三关制作，先修正关卡目标、反馈和 Python 教学节奏。
- 某项健壮性工作连续两次没有复现真实玩家问题：从首版范围删除，不继续追加防御代码和测试。
