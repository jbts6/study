# 奥术工业幻想 Python RPG 设计

## 状态

设计已根据书面审查和开源复用调研完成修订，等待用户审阅修订版。本文定义首个可玩切片的产品边界与关键契约，不是实现计划。

## 目标

为已经具备其他语言编程经验、但不熟悉 Python 的成年人，提供一款真正可玩的回合制战术 RPG。玩家通过探索、战斗、调试和自动化逐步掌握 Python 的写法、惯用法和运行模型。

Python 是玩家在世界中施法、操控队友、修复机关和制定战术的真实工具，而不是附加在题库上的积分系统。

## 非目标

- 不做编程启蒙，不重复解释变量、循环和函数的通用概念。
- 首版不做账号、云端存档、多人联机或公开远程代码执行。
- 首版不同时上线 Go 和 Rust。
- 首版不实现开放世界、复杂经济、装备词缀、数据科学库或异步 Python。
- 首版以个人桌面浏览器和本机开发服务器为运行边界，不提供公共托管、移动端代码编辑或素材再分发。
- 首版不为 Go 和 Rust 创建空目录、占位运行器或提前抽象语言专属能力。
- 不把现有 `python/` 课程页面直接改造成 RPG；现有课程继续独立可用。

## 用户与成功标准

### 目标用户

已有 JavaScript、Go、Java、C# 等语言经验，想快速进入 Python 真实项目的成年人。

### 首版成功标准

- 使用干净存档进行端到端验收时，目标玩家可以在包含据点、失败重试和 Boss 在内的 60～90 分钟内完成独立战役切片。
- 玩家必须用 Python 完成变量与属性读取、布尔表达式、条件、循环、集合、函数、默认参数和推导式等六组任务；异常、生成器、模块和测试进入完整 Python 战役。
- 玩家能看到代码执行轨迹：代码行、变量值、角色动作和战局变化互相对应。
- 同一个初始状态、已接受动作序列和随机状态可以重放到完全相同的逐步状态哈希，失败原因可定位到第一处偏差。
- 学习收益会改变玩法：从手动行动逐步升级为技能函数、条件策略和整队自动化。

## 核心体验

玩家扮演规则工程师，在奥术工业大陆中修复失控的规则炉心。

核心循环：

```text
探索城镇与遗迹
→ 接受有实际战斗目标的任务
→ 观察敌人、地形与队友状态
→ 手动行动或修改 Python 战术
→ 运行代码并逐步回放战斗
→ 根据代码行、变量和事件轨迹调试
→ 获得装备、技能槽与自动化能力
→ 重构战术，应对更复杂的战场
```

编码参与度采用渐进式自动化：

- 前期：修改参数、补全表达式，熟悉 Python 语法差异。
- 中期：编写条件、循环、函数和推导式，形成可复用战术。
- 后期完整战役：加入异常策略、生成器、模块和测试，组合队友 AI 与资源调度。

玩家失败时看到的不是单一“答案错误”，而是具体代码行执行后哪个角色做了什么、变量如何变化、战局为何崩溃。

## 世界与语言战役

世界是一座由规则炉心维持的奥术工业大陆。炉心失衡后，三个区域出现不同灾害。三条战役共享主角、队友、装备外观、世界地图、主线事件、成就、存档和战斗回放格式；不共享代码、课程顺序、运行器、语言专属敌人机制和 Boss 判定。

- **Python：变形沼泽与自动化遗迹**
  - 主题：快速试错、动态数据、自动化。
  - 重点：Python 数据模型、可迭代对象、推导式、函数式工具、异常、模块与脚本工程。
- **Go：并发工坊与物流城邦**
  - 主题：多人协作、任务调度、稳定服务。
  - 重点：显式错误、接口、结构体、goroutine、channel、`select`、HTTP 和测试。
- **Rust：所有权熔炉与边界要塞**
  - 主题：资源所有权、契约和高可靠系统。
  - 重点：所有权、借用、生命周期、`Option`、`Result`、trait、迭代器、线程安全和异步。

解锁顺序为 Python → Go → Rust；已经掌握某门语言的玩家可以跳过剧情教学，只保留诊断测试和战斗关卡。

## 首发垂直切片

- 1 个据点：锈叶前哨站。
- 1 张地牢地图：失控的自动化遗迹。
- 3 个普通敌人：护甲傀儡、巡逻蜂群、过热核心。

关卡与 Python 能力映射：

| 关卡 | Python 重点 | 游戏目标 |
|---|---|---|
| 1 | 变量、属性读取、布尔表达式 | 让侦察兵避开危险地格 |
| 2 | `if / elif / else` | 根据敌人护甲选择攻击 |
| 3 | `for`、`range`、列表和字典 | 依次修复多个节点并管理目标 |
| 4 | 函数与默认参数 | 制作可复用的目标选择函数 |
| 5 | 推导式与排序 | 筛选威胁并安排队伍行动 |
| 6 | 综合 Boss | 组合前五关能力击败递归炉心 |

## 首版战斗契约

### 状态模型

`BattleState` 是战斗事实的唯一来源。界面、Python 代码、动画和回放都不能直接修改它，只能提交 `Action`，由战斗归约器验证并生成下一状态。

首版 `BattleState` 至少包含：

- `battleId`、`contentVersion`、`revision`、`round`、`turnIndex` 和当前阶段。
- 单位的 `id`、阵营、位置、生命、攻击、防御、移动距离、先手、技能与冷却。
- 地图尺寸、不可通行格、危险格、掩体格和可修复目标。
- 任务目标、失败条件、当前随机数生成器状态和最终结果。

`WorldView` 是从 `BattleState` 派生的不可变 JSON 投影，只暴露当前关卡允许玩家观察的字段。它不包含可调用代理、引擎对象或隐藏敌人信息。首版战斗数值全部使用整数，避免跨运行时浮点差异。

### 动作结构

`Action` 是严格校验的 JSON 判别联合。所有动作都必须包含 `type`、`actorId` 和 `expectedRevision`；未知字段、缺失字段、非整数坐标和与当前 `WorldView.revision` 不一致的动作一律拒绝。

| `type` | 额外字段 | 语义 |
|---|---|---|
| `move` | `path: Array<{x, y}>` | 路径不包含起点，每一格必须与前一格正交相邻，长度不能超过单位移动距离 |
| `attack` | `targetId` | 使用单位普通攻击命中一个合法目标 |
| `cast` | `skillId`，以及技能规定的 `targetId` 或 `targetCell` 二选一 | 施放一个未冷却且资源足够的技能 |
| `guard` | 无 | 获得固定防御加成，持续到该单位下一回合开始 |
| `wait` | 无 | 不产生战斗效果，只推进回合 |

### 回合流程

每轮按单位先手从高到低排序；先手相同时按稳定的单位 ID 升序排序。每个存活单位在自己的回合只提交一个动作：

1. 引擎从当前 `BattleState` 生成带 `revision` 的 `WorldView`。
2. 手动控制或 Python Runner 产生一个 `Action`；两种控制方式使用完全相同的动作结构。
3. 纯函数 `validateAction(state, action)` 依次校验结构、`expectedRevision`、行动者、路径、距离、目标、冷却和资源消耗。
4. 校验通过后，纯函数 `reduceBattle(state, action)` 生成新状态和 `BattleEvent[]`，按规则需要消费随机数，并将 `revision` 递增一。
5. 引擎计算规范化状态哈希，再进入下一单位回合。

非法动作不修改状态、不消耗回合，也不被写入已接受动作日志。自动战斗会暂停，并把拒绝原因、相关字段和对应代码轨迹返回给玩家修改。

### 最小规则集

- 地图使用正交方格和曼哈顿距离，不允许斜向移动；路径不能穿过单位或不可通行格。
- 每回合只允许 `move`、`attack`、`cast`、`guard`、`wait` 之一，不支持移动后再攻击。
- 普通伤害为 `max(1, 攻击者攻击 + 技能威力 - 目标防御)`；首版没有命中率、暴击、浮点倍率或随机伤害。
- 危险格在单位回合结束时造成固定伤害；掩体仅提供固定防御加成；可修复目标使用整数耐久度。
- 技能只包含作用距离、固定威力、冷却、目标类型和可选状态效果；状态效果按稳定 ID 顺序结算。
- 消灭规定敌人或完成关卡目标即胜利；全队失去行动能力、关键目标被摧毁或超过关卡回合上限即失败。
- 失败后从关卡初始快照重开；首版不提供战斗中途存档。

每个 `BattleEvent` 至少包含事件协议版本、动作内单调递增的 `seq`、产生它的状态修订号、稳定事件类型和 JSON 载荷。首版事件类型固定为移动、伤害、治疗、状态增减、冷却变化、目标进度、单位失能、回合切换和战斗结束；界面动画只能消费这些事件，不能反推或修改战斗状态。

## 技术架构

首发为独立的 TypeScript Web 应用，本地优先，通过构建工具管理 Worker 和依赖；现有 `python/` 课程保持不变。

```text
rpg/
├── src/
│   ├── game/
│   │   ├── world/             # 地图、单位、地形和任务投影
│   │   ├── combat/            # 状态、动作校验、纯归约器和事件
│   │   ├── replay/            # 动作日志、规范化哈希和验证
│   │   ├── progression/       # 奖励、技能槽和解锁
│   │   └── save/              # 版本化本地存档
│   ├── runners/
│   │   ├── protocol/          # 与语言无关的请求、结果和诊断
│   │   └── python/            # PythonRunnerAdapter 与 Worker
│   └── ui/                    # 战场、编辑器、轨迹和反馈
├── content/
│   ├── shared/                # 世界、地图、敌人和通用任务
│   └── python/                # Python 关卡、模板和断言
└── tools/
    └── content-check/         # 内容、协议和资源校验
```

游戏内核不解析 Python，也不知道 Pyodide。运行器不决定动作是否合法或关卡是否通过。界面只消费 `BattleState`、`BattleEvent` 和诊断，不保存另一份可变战斗状态。

### 复用决策

调研日期为 2026-08-10，采用“选择性复用”路线：

| 项目 | 决策 | 使用边界 |
|---|---|---|
| [`pyodide-worker-runner`](https://github.com/alexmojaki/pyodide-worker-runner) | 直接依赖并固定版本 | 只负责 Worker 通信、中断、致命错误重载和虚拟文件系统，由 `PythonRunnerAdapter` 隔离其 API |
| [Pyodide](https://github.com/pyodide/pyodide) | 直接依赖并固定实现版本 | 调研时 npm 可安装基线为 `314.0.3`；GitHub 最新发布标签 `314.0.4` 尚未同步到 npm，不使用浮动 `latest`，也不得为了兼容辅助库而降级运行时 |
| [boardgame.io](https://github.com/boardgameio/boardgame.io) | 不直接依赖 | 借鉴纯状态归约、非法动作、持久化随机状态和动作日志设计 |
| [CodeCombat](https://github.com/codecombat/codecombat) | 不直接依赖 | 借鉴多文件代码映射、固定种子、Worker 模拟、逐帧哈希和目标状态分离 |
| [futurecoder](https://github.com/alexmojaki/futurecoder) / [okpy/pytutor](https://github.com/okpy/pytutor) | 不直接依赖 | 借鉴 Worker 集成、错误诊断和结构化代码轨迹字段；只参考契约，不复制实现 |

实现的首个证明点是让 `pyodide-worker-runner@1.4.0` 与 npm 可安装的 `pyodide@314.0.3` 通过加载、执行、中断、超时重建和多文件导入测试。开始实现时先复查 npm 稳定版；若版本已更新，则只在同一证明集全部通过后固定新版本。若辅助库不兼容，则保留 `PythonRunnerAdapter` 契约，改用 Pyodide 官方 Worker API 实现适配器；证伪后不得继续修补依赖内部或回退 Pyodide。

### Worker 生命周期与限制

Python Worker 的状态固定为 `loading`、`ready`、`running`、`interrupting`、`restarting` 和 `unavailable`。每次运行使用独立工作目录和全新模块命名空间，不继承上次运行的变量、导入缓存或标准输出。

- 优先通过 `SharedArrayBuffer` 和 Pyodide 中断缓冲区发出可恢复中断。
- 到达硬超时后始终终止 Worker 并重建，不假设 `KeyboardInterrupt` 能中断所有阻塞调用。
- 关卡声明 `allowedModules`；默认禁止 `js`、`pyodide`、`micropip`、网络、进程和浏览器存储访问。
- 不调用按源码自动安装依赖的能力。课程所需包由应用固定版本并在启动阶段预载。
- 标准输出、标准错误、轨迹条数、单值深度、文件数量和源码总大小都受请求预算限制。
- Worker 只收发结构化克隆数据，不接收 DOM、存储对象或游戏引擎实例。
- Worker 隔离和模块白名单是稳定性边界，不是对抗恶意代码的安全沙箱；同源应用不得放入秘密、特权令牌或只有前端限制保护的敏感能力。

## 统一执行协议

一次 Runner 调用只负责在一个单位回合中执行指定入口并返回一个动作意图。Runner 接收不可变 `WorldView`，不能直接推进战斗。

### 执行请求

```json
{
  "protocolVersion": 1,
  "runId": "run-01J8K3",
  "attemptId": "python-marsh-03-attempt-2",
  "questId": "python-marsh-03",
  "language": "python",
  "files": {
    "main.py": "def choose_action(world):\n    return {'type': 'wait', 'actorId': world['activeUnitId'], 'expectedRevision': world['revision']}\n"
  },
  "entrypoint": {
    "file": "main.py",
    "callable": "choose_action"
  },
  "worldView": {
    "battleId": "automation-ruin-03",
    "revision": 7,
    "round": 2,
    "activeUnitId": "scout",
    "units": [],
    "objectives": []
  },
  "allowedModules": ["math"],
  "limits": {
    "timeoutMs": 2000,
    "maxTraceEvents": 1000,
    "maxOutputBytes": 16384,
    "maxSourceBytes": 65536
  }
}
```

`files` 从首版开始就是映射而非单个源码字符串，使后续模块与测试关卡无需修改协议。入口文件必须存在于映射内，所有路径必须是相对路径且不能包含父目录跳转。

### 执行结果

```json
{
  "protocolVersion": 1,
  "runId": "run-01J8K3",
  "attemptId": "python-marsh-03-attempt-2",
  "executionStatus": "completed",
  "returnValue": {
    "type": "wait",
    "actorId": "scout",
    "expectedRevision": 7
  },
  "returnValueTraceSeq": 12,
  "trace": [
    {
      "seq": 12,
      "file": "main.py",
      "line": 2,
      "event": "return",
      "function": "choose_action",
      "locals": {}
    }
  ],
  "diagnostics": [],
  "streams": {
    "stdout": "",
    "stderr": "",
    "truncated": false
  },
  "metrics": {
    "durationMs": 18,
    "traceEvents": 2
  }
}
```

`executionStatus` 只允许 `completed`、`syntax_error`、`runtime_error`、`timeout`、`interrupted`、`invalid_request`、`runner_error`。`completed` 只表示 Python 正常返回了可跨 Worker 传输的 JSON 值，不表示动作有效或关卡通过。无法安全转换的 Python 返回值使用 `runtime_error` 和稳定诊断码 `RETURN_NOT_SERIALIZABLE`。

Runner 不解释 `returnValue` 的动作语义。游戏内核把它解析为单个 `Action`，随后产生独立的 `ActionResolution`：`accepted` 时包含战斗事件和新状态哈希，`rejected` 时包含稳定错误码、字段路径和可读解释。关卡结果只允许 `in_progress`、`won`、`lost`，由游戏内核在状态迁移后计算。每条 `diagnostics` 必须包含稳定 `code`、`severity` 和消息；定位信息存在时再包含文件、行和列。

### 代码轨迹协议

轨迹使用 Python 标准追踪机制，只记录玩家文件中的 `call`、`line`、`return` 和 `exception`。每条 `TraceEvent` 包含单调递增序号、文件、行号、函数、调用深度和经过裁剪的局部变量。

- 字符串最多 200 个字符，集合最多 20 项，对象最多 3 层；超出部分写入明确的截断标记。
- 不读取私有属性、描述符或任意 `repr`，避免轨迹本身触发用户代码。
- 不记录运行器内部帧、模块对象、引擎对象或未在关卡观察白名单中的字段。
- 达到轨迹预算后停止运行并返回 `runtime_error` 和 `TRACE_LIMIT_REACHED`，不能悄悄丢弃后续步骤。
- `returnValueTraceSeq` 将动作意图关联到产生它的代码位置；引擎生成的 `BattleEvent` 再关联到该动作和状态版本。

## 重放契约

战斗重放以关卡初始状态和已接受动作日志为事实来源，不重新运行玩家 Python。这样代码改动、运行时升级或轨迹显示变化不会改变既有战斗回放。

```json
{
  "replayVersion": 1,
  "engineVersion": "0.1.0",
  "contentVersion": "python-slice-1",
  "runnerProtocolVersion": 1,
  "pythonRuntimeVersion": "314.0.3",
  "questId": "python-marsh-03",
  "battleId": "automation-ruin-03",
  "seed": "1842",
  "initialState": {},
  "initialStateHash": "sha256:...",
  "steps": [
    {
      "seq": 1,
      "round": 1,
      "turnIndex": 0,
      "stateRevision": 0,
      "actorId": "scout",
      "action": {"type": "wait", "actorId": "scout", "expectedRevision": 0},
      "rngBefore": "...",
      "rngAfter": "...",
      "events": [],
      "eventsHash": "sha256:...",
      "stateHash": "sha256:..."
    }
  ],
  "outcome": "won",
  "finalStateHash": "sha256:..."
}
```

状态和动作使用 JSON Canonicalization Scheme 规范化，再以 SHA-256 计算哈希。随机数只能由战斗内核的单一生成器产生，每一步同时记录前后随机状态。首版状态只使用整数、布尔值、字符串、数组和键排序对象。

验证重放时，从 `initialState` 依次应用已接受动作，并在每步比较随机状态、`eventsHash` 和 `stateHash`。第一处不一致即停止，报告步骤、字段、期望值、实际值和版本信息。视觉播放可以消费通过结构校验的已保存 `BattleEvent`，但哈希不一致的重放必须标为未验证。首版不在重放中保存或重新运行历史 Python；关卡草稿和当前尝试轨迹由存档与执行结果分别管理，不作为战斗重放成立的前提。

引擎或内容版本不兼容时，不声称验证通过。只要事件数据仍可解析，可以提供只读播放；无法解析时保留原始导出文件并给出版本错误。

## 存档契约

首版使用 `localStorage`，但所有调用必须经过 `SaveStore`。存档采用单一版本化信封：

- `schemaVersion`、单调递增 `revision`、更新时间和内容校验和。
- 战役进度、装备与解锁、每关代码草稿、界面偏好和最近重放索引。
- 当前版本最多保留 5 个完整重放；达到 3 MB 软上限后优先删除最旧重放，不删除进度与草稿。

写入时先保存新一代记录并读回校验，再切换活动指针；成功后保留上一代作为恢复副本。读取失败时依次尝试上一代、用户导入文件和新存档，任何恢复都必须显式告知原因，不能静默重置。

存档支持导出和导入 JSON。导入前校验结构、版本、校验和、关卡 ID 和源码大小；迁移函数必须逐版本执行并保留原始备份。首版不保存战斗中间状态。

## 首版界面边界

首版桌面界面同时呈现战场、代码编辑器和轨迹/诊断区域，主要验收视口为 1280×720 与 1440×900。战场始终是主要空间，代码和轨迹可以折叠但不能遮挡当前单位、运行状态或错误位置。

- 手动动作与运行代码使用同一战场反馈和回放控件。
- 运行期间保持编辑器内容可读，明确显示加载、运行、中断、重启和存档失败状态。
- 键盘可以完成编辑、运行、暂停、逐步回放和返回编辑；所有焦点可见。
- 动画仅消费 `BattleEvent`，在减弱动效设置下改为即时状态切换。
- 小于首版最小桌面宽度时只保证查看战场、轨迹和存档导出，不承诺移动端代码编辑。

## 素材策略

首发视觉基线为 Tiny Swords 的 64px 战棋尺度，后续使用铜管机械、符文能源和深色遗迹地表做奥术工业化改造，不混入 Ninja Adventure 的 16px 像素密度。

- Tiny Swords：必须记录实际使用的包名和版本；旧版 CC0 包与当前自定义许可包不能只用同一个品牌名代替。当前包可用于个人和商业项目并修改，但不得重新分发或单独转售素材包。
- Kenney：资产页标注 CC0，可用于商业项目且无需署名。
- Ninja Adventure：CC0，可作为备用的角色、怪物、Boss、音效和 UI 素材来源，但不作为首发主视觉。
- OpenGameArt：仅使用逐项明确标注许可证的资源，并在资产清单中记录作者、来源、许可证和修改说明。

素材目录必须维护 `ASSET-LICENSES.md`，记录包名、下载日期、来源、许可证快照、文件哈希和修改说明。禁止引入无法确认授权的图片、音乐、字体或生成素材；即使项目只供个人使用，也不能让来源记录依赖网页未来仍然可访问。

## 状态与错误处理

必须分别覆盖应用加载、Worker 加载、就绪、运行、中断、Worker 重建、语法错误、运行错误、超时、动作拒绝、战斗胜负、进度保存失败和存储损坏。标准输出为空不是错误；只要入口正常返回有效动作，就可以继续校验。

所有错误包含稳定错误码、用户可读解释、可用的文件与行号、关联轨迹范围和明确恢复动作。运行器不得把本机绝对路径、环境变量、Worker 内部栈或敏感信息返回页面。Runner 不可用时可以保留手动战斗和代码草稿，但代码关卡必须明确暂停，不能伪装成通过或静默切换为答案模式。

## 测试策略

- 依赖证明：固定的 `pyodide@314.0.3` 与 `pyodide-worker-runner@1.4.0` 完成加载、执行、中断、硬超时重建、多文件导入和连续运行隔离；若实现时升级 Pyodide，则对新版本重跑同一证明集。
- 游戏内核：每种动作的合法与非法表格测试、稳定先手、整数伤害、状态效果顺序、胜负条件和纯状态迁移。
- 确定性：固定初始状态和动作序列必须逐步产生相同随机状态、事件和 SHA-256 状态哈希。
- 重放：完整重放、版本不兼容、首步/中段哈希偏差、损坏日志和只读事件播放。
- 运行器协议：正常返回、语法错误、运行错误、无输出、错误返回类型、轨迹上限、输出截断、超时、主动中断、Worker 不可用和非法路径。
- 轨迹：递归、循环、异常、多文件、循环引用、超长集合和恶意 `repr`，确认限制生效且不记录内部帧。
- 存档：双代写入、校验失败回退、逐版本迁移、容量回收、导入导出和存档往返。
- 内容校验：关卡 ID、能力标签、动作白名单、观察字段、隐藏断言、回合上限和资源许可证清单。
- 浏览器验收：1280×720 与 1440×900 下的代码编辑、手动/自动动作、运行状态、错误定位、逐步回放、键盘操作、减弱动效、进度与草稿保存。
- 端到端验收：用干净存档完成六个遭遇，记录总时长、重试点和每项 Python 能力是否真实影响战斗结果。

## 后续路线

1. 先完成 Pyodide 兼容性证明和 `PythonRunnerAdapter` 契约测试；失败时立即切换到官方 Worker API 适配器。
2. 实现纯战斗归约器、动作校验、确定性随机状态和最小重放验证，不接入界面素材。
3. 接入 Python Worker、受限轨迹和单回合 `choose_action(world)`，证明代码能稳定产生并解释一个动作。
4. 完成六个遭遇、桌面界面、版本化存档和端到端验收。
5. 用实际游玩验证“代码能力是否带来自动化成长”，再扩展异常、生成器、模块和测试等完整 Python 战役。
6. Python 战役稳定后，再分别设计 Go 与 Rust 的运行器和语言专属机制，不预先创建占位实现。
7. 最后评估可选在线 Runner、云存档和公共发布；它们不反向约束首版本地架构。
