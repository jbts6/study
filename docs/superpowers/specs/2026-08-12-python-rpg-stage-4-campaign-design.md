# Python RPG 阶段 4 六关战役设计

## 结论

阶段 4 在现有单屏应用和战斗内核上增加六关固定战役。玩家始终只控制主角 `scout`，通过逐步减少的脚手架学习读取字典、条件分支、循环筛选、复合条件、辅助函数和综合策略。

内容使用类型化 TypeScript 数据。关卡只引用三种敌方职责和五项奖励能力；目标用途直接复用现有 `Objective.key`。不建设通用关卡 DSL、行为树、寻路系统、目标子系统或角色成长系统。

前三关先形成可玩垂直切片。确认教学与战术循环成立后，再沿同一契约制作后三关。

## 目标

- 交付 `python-marsh-01` 至 `python-marsh-06` 六关可离线战役。
- 面向只会输入和运行代码的 Python 初学者，每关只增加一个主要编程负担。
- 保持单主角玩法，通过能力解锁增加战术选择。
- 让任务说明、提示、战斗反馈、结算和刷新恢复形成完整学习循环。
- 每关都有初始战斗、任务目标、脚手架、固定规则、终局断言、参考解法和奖励。
- 最小扩展现有 `AppController`、`resolveTurn`、本地 Runner 和单份本地存档，不引入第二个战役状态源。

## 非目标

- 队友、任务 NPC、多角色代码轮转或角色能力分配。
- 装备、货币、永久属性、技能树或关卡选择。
- 通用敌方 AI、行为树、完整寻路、范围伤害、召唤或强制位移。
- 通用 schema、decoder、规则表达式、脚本化断言或内容编辑器。
- 分析玩家源码是否使用 `if`、`for` 或辅助函数。
- 保存每关历史草稿、旧版本存档迁移、导入导出或多存档槽。
- 移动端重做、远程执行、云端存档或遥测。

## 教学与能力曲线

| 关卡 | Python 教学 | 战术问题 | 通关奖励 |
|---|---|---|---|
| `python-marsh-01` | 读取 `world` 字典并返回合法指令 | 移动、攻击并阻止敌人腐化中继器 | `ward` |
| `python-marsh-02` | 用 `if` 根据当前状态选择行动 | 在危险地形、攻击、自疗和防御之间取舍 | `pierce` |
| `python-marsh-03` | 用 `for` 遍历并筛选优先敌人 | 从多名敌人中选择目标，并在胜利前激活印记 | `renew` |
| `python-marsh-04` | 用 `and`、`or`、`not` 组合条件 | 在救援中继器、破防、自疗和激活封印之间排序 | `fracture` |
| `python-marsh-05` | 用辅助函数拆分目标和行动选择 | 对付猎手与守卫，并依次激活两处节点 | `aegis` |
| `python-marsh-06` | 综合前五关知识 | 同时处理三类敌人、危险地形、中继器与最终封印 | 战役完成 |

基础能力继续使用阶段 3 已有的 `spark` 和 `mend`。所有解锁能力只注入 `scout`，不创建全队共享能力池。

## 六关内容

### 第一关：唤醒中继器

- 脚手架：提供完整 `choose_turn` 骨架、明确填空位置和 `wait` 示例。
- 敌人：一名腐化者，只接近并腐化中继器。
- 任务：在中继器被毁前消灭敌人。
- 终局断言：中继器仍有耐久。
- 奖励：`ward`。

### 第二关：毒沼岔路

- 脚手架：提供完整函数骨架和一个非答案式 `if` 示例。
- 敌人：一名腐化者；地图加入危险格与安全绕行路线。
- 任务：根据生命、位置和危险格选择攻击、自疗、防御或移动。
- 终局断言：中继器仍有耐久。
- 奖励：`pierce`。
- 边界：玩家只知道哪些格子危险，不要求根据未公开的具体伤害数值计算路线。

### 第三关：勘测印记

- 脚手架：提供遍历 `world["units"]` 的 API 示例，不提供完整函数。
- 敌人：多名猎手，均追击 `scout`。
- 任务：遍历可见敌人，根据生命、距离或防御状态选出优先目标；消灭最后一名敌人前激活勘测印记。
- 终局断言：勘测印记已经激活。
- 奖励：`renew`。

### 第四关：双重封锁

- 脚手架：提供 API 速查和非答案式复合条件示例，不提供入口函数骨架。
- 敌人：一名腐化者进攻中继器，一名守卫保护封印。
- 任务：在救援中继器、破防、自疗和激活封印之间建立行动优先级。
- 终局断言：封印已激活，中继器仍有耐久。
- 奖励：`fracture`。

### 第五关：裂隙节点

- 脚手架：只提示可将“选敌人”“选目标”“选行动”拆成辅助函数，不给出函数骨架。
- 敌人：猎手追击 `scout`，守卫保护节点。
- 任务：使用 `fracture` 处理高防目标，在生存、输出和交互之间切换，依次激活两处节点。
- 终局断言：两处节点均已激活，中继器仍有耐久。
- 奖励：`aegis`。

### 第六关：沼心封印

- 脚手架：只保留任务说明和 API 速查，不提供解法结构。
- 敌人：腐化者、猎手和守卫各自执行固定职责。
- 任务：综合使用全部已解锁能力，在最大回合数内激活最终封印并消灭敌人。
- 终局断言：最终封印已激活，中继器仍有耐久。
- 奖励：保存最终胜利战斗并显示可刷新恢复的战役完成结算，不发放没有后续使用场景的新能力。

所有关卡仍由战斗内核按现有顺序以敌方全部失能判定 `won`，或以主角失能、关键目标归零、超过最大回合数判定 `lost`。关卡终局断言只补充内核不知道的任务条件，不重复表达内核胜负规则；不为极少见的同时结算修改战斗内核。

## 内容契约

```ts
type LevelDefinition = Readonly<{
  id: LevelId;
  title: string;
  briefing: readonly string[];
  starterCode: string;
  apiHints: readonly string[];
  initialBattle: BattleState;
  enemyBehaviors: Readonly<Record<string, EnemyBehaviorSpec>>;
  reward: LevelReward;
}>;

type EnemyBehaviorSpec =
  | Readonly<{ type: "corrupt" }>
  | Readonly<{ type: "hunt-player" }>
  | Readonly<{ type: "guard" }>;

type LevelReward =
  | Readonly<{ type: "ability"; abilityId: AbilityId }>
  | Readonly<{ type: "campaign-complete" }>;
```

交互权限和终局检查直接从 `Objective.key` 派生：主角只能操作非关键目标，腐化者只能操作该关唯一的关键目标。规则拒绝时不调用 `resolveTurn`，不推进战斗，并向玩家显示具体原因。含关键目标的关卡必须启用现有 `keyObjectiveDestroyed` 失败条件；战斗内核继续按现有顺序判定阶段，不为同时结算增加特殊状态。内核胜利后只补查所有非关键目标是否已经完成。

关卡数据初始化时只检查必填字段、重复关卡 ID，以及单位、目标和能力的实际引用。下一关由固定的六关顺序推导，不在数据中重复保存。`initialBattle` 已由 TypeScript 类型约束，不再搭建通用加载器或第二套运行时解码器。

## 目标语义

战斗内核继续使用现有 `Objective`：

- `key: true` 即 `protect`：中继器。只有对应腐化者可执行 `interact`；耐久归零表示中继器被毁。
- `key: false` 即 `activate`：印记、节点或封印。只有 `scout` 可执行 `interact`；耐久归零且 `completed` 为真表示激活完成。

UI 根据 `key` 把通用交互事件翻译为“中继器受到腐化”或“封印激活进度”，不直接向玩家展示容易误解的底层事件名称。不新增目标阵营、目标攻击或目标修复规则。

## 能力目录

能力集中定义在一份只读 `AbilityCatalog`。它是能力 ID 到现有 `Skill` 字段补丁的静态映射，不演化为独立能力系统：

| 能力 | 现有字段表达 | 固定语义 |
|---|---|---|
| `ward` | 单位目标 `heal`，射程 0，威力 1，冷却 1；防御 `+2`，持续 1 回合 | 少量自疗并获得短时防御 |
| `pierce` | 单位目标 `damage`，射程 1，威力 4，冷却 2 | 高伤害近战法术，不宣称无视防御 |
| `renew` | 单位目标 `heal`，射程 0，威力 5，冷却 2 | 更强的自疗 |
| `fracture` | 单位目标 `damage`，射程 1，威力 1，冷却 2；防御 `-2`，持续 2 回合 | 造成伤害并暂时削弱防御 |
| `aegis` | 单位目标 `heal`，射程 0，威力 3，冷却 2；防御 `+2`，持续 2 回合 | 自疗并获得持续防御 |

数值只使用现有 `damage`、`heal` 和 `defenseBonus` 结算。阶段 4 不为能力增加新效果类型。

`AbilityCatalog` 是五项奖励能力字段的唯一来源。创建或重试关卡时，先从关卡初始战斗读取基础技能，再按固定关卡顺序将已获能力补丁组装到 `scout.skills` 一次；读取已有存档时不重复注入。能力仍只使用现有 `damage`、`heal`、`defenseBonus` 和冷却字段。

## 敌方行为

敌人严格执行内容职责，不因主角接近而临时改变目标。每回合先决定最多一个相邻移动格，再从移动后的落点选择主行动，以此生成一条完整 `TurnCommand`：

- `corrupt`：向配置的中继器移动；移动后相邻则执行腐化，否则 `guard`。
- `hunt-player`：向 `scout` 移动；移动后在普通攻击范围内则攻击，否则 `guard`。
- `guard`：不移动；`scout` 在普通攻击范围内时攻击，否则 `guard`。

腐化者和猎手若在移动前已经满足职责动作条件，则不移动并直接执行动作。否则移动只做单步贪心选择：枚举合法相邻格，选择让曼哈顿距离最短的一格；距离相同时按 `y`、再按 `x` 升序选择。没有合法移动时执行 `guard`。固定地图负责保证参考路线可达，不建设完整寻路和动态绕障。

## 玩家视图与提示

`WorldView` 保持现有结构，只在友方技能投影中增加 `remainingCooldown`。不公开敌方隐藏属性，也不增加 `hazardDamage`。

任务区始终显示：

- 当前关卡目标与失败约束。
- `scout` 当前可用能力和冷却状态。
- 与本关匹配的 API 速查。
- 可按需展开的概念提示。

提示随关卡递减。参考解法只存在于测试代码，不打包到运行时内容，也不在 UI 中提供“一键解答”。

## 回合与结算流程

1. 冻结当前代码和战斗快照，并运行本地 Python。
2. 将返回值解析为候选 `TurnCommand`。
3. `AppController` 通过一个纯 `validateLevelCommand(level, state, command)` 检查目标用途等指令前规则。
4. 规则通过后调用 `resolveTurn`。
5. 自动执行敌方确定性回合；一个纯 `enemyCommand(level, state)` 只按三种固定职责生成指令，每条指令同样经过 `validateLevelCommand`。
6. 若战斗仍在进行，保存战斗、代码和战役进度并返回编辑状态。
7. 若内核为 `lost`，进入任务失败结算。
8. 若内核为 `won`，检查当前关卡终局断言；全部通过才进入通关结算，否则由视图和结算面板共同显示任务失败，不发放奖励或进入下一关。

通关、任务失败和战役完成都在现有底部反馈区展开为结算面板。结算由当前关卡、战斗阶段和终局断言即时推导，不保存独立结算状态。面板保留最终战场和代码供复盘，禁用编辑器与运行按钮：

- 前五关通关：显示完成条件、回合摘要和新能力，提供“进入下一关”。
- 任务失败：逐条显示失败原因，提供“重试本关”。
- 第六关通关：显示结局摘要，只保留“重置存档”。

Python 语法错误、运行时错误、非法指令、超时和中断不会推进战斗，仍显示在普通反馈区，不进入任务失败结算。

`AppController` 继续是唯一应用快照源：它把当前关卡 ID 从首关常量扩展为六关联合类型，并新增“重试本关”和“进入下一关”两个窄操作。`app-view` 只在终态增加结算按钮和只读呈现，不创建新页面、路由或独立 UI 状态模型。

## 重试、切关与刷新

- 重试使用当前 `LevelDefinition.initialBattle` 重建战斗，保留本关代码草稿。
- 前五关通关时只保存胜利战斗和当前代码；奖励、结算和已获能力从固定关卡顺序、战斗阶段和终局断言即时推导，刷新后仍停留在同一结算面板，也不会重复发奖。
- 玩家点击“进入下一关”后，才更新关卡 ID、创建下一关初始战斗并加载下一关脚手架。
- 进入下一关会替换当前草稿；首版不能返回旧关，不保存历史草稿。
- 第六关完成后保留最终战斗、代码和完成状态；显式重置才重新开始。

## 存档设计

阶段 4 使用 V2 存档：

```ts
type SaveDataV2 = Readonly<{
  version: 2;
  currentLevelId: LevelId;
  battleState: BattleState;
  codeDraft: string;
}>;
```

不保存 `unlockedAbilityIds`、`campaignCompleted`、`completedLevelIds`、断言缓存、历史草稿或角色成长状态。已解锁能力由固定六关顺序、当前关卡和当前结算即时推导；最后一关的已结算胜利即为战役完成状态。V1 不迁移；读取到 V1、未知版本或损坏字段时进入现有存档恢复页，玩家输入“重置存档”后创建全新 V2。

读取 V2 时只检查版本、关卡、代码草稿和战斗状态必要字段。战斗 ID 必须与当前关卡匹配。

## 本地代码与安全边界

阶段 4 沿用阶段 3 的本地 Runner 契约，不改动本地代码执行边界。完整 spec 与实施 plan 定稿后，再单独执行一次安全审查；设计不为它预建额外状态机或协议字段。

## 测试与验证

测试只覆盖正常主流程和一个关键失败路径：

- 一组数据校验测试覆盖六关必填字段、重复 ID 和实际引用。
- 六份参考解法通过同一参数化流程，分别证明每关可以通关。
- 一个终局断言失败用例证明“敌人全灭但封印未激活”不会发奖或解锁下一关。
- 一个存档流程覆盖 V2 刷新恢复和显式进入下一关。
- 前三关垂直切片完成时运行定向测试和构建，不提前运行全量六关流程。
- 六关完成后运行一次 Playwright 主流程，从第一关打到第六关，检查解锁、结算和刷新恢复。

不为每种敌人排列、每个断言组合、重复关闭、跨版本迁移或多视口建立测试矩阵。

## 阶段完成标准

- 前三关先形成完整的编写、运行、反馈、通关、奖励和刷新恢复循环。
- 六关均能由各自参考解法通关，错误参考结果不会推进战斗。
- 能力按 `ward → pierce → renew → fracture → aegis` 从关卡进度推导并注入 `scout`。
- 任务失败提供具体原因，重试保留当前代码草稿。
- 第六关完成状态可以刷新恢复，且不会发放无后续用途的新能力。
- 生产构建不包含参考解法、远程代码路径、未使用内容框架或本机绝对路径。
